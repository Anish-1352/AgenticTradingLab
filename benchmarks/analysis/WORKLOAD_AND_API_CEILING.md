## Why the $50K figure never pinned down

### LEADERBOARD — neither workload

**Recurring cost today is `$0`** [MEASURED] — but by deliberate pause, not by absence. Upstream ships `.github/workflows/daily-leaderboard.yml` with a weekday cron whose whole `schedule:` block is commented out, and `workflow_dispatch` defaults `deploy_models=false` [MEASURED]. Its own comment gives the reason: *"left on schedule it would keep deploying every competition LLM nightly, billable, for a board nobody can open."* Earlier phases reported that no scheduler existed; that was true of this branch and is no longer true of upstream.

**The pause is one uncomment from a recurring bill**, so the counterfactual is worth pricing. A scheduled run always sets `deploy_models=true`, deploying all seven models over a rolling one-day window every weekday [MEASURED]:

| cadence | per run | per month if re-enabled | Tier |
|---|---:|---:|---|
| hourly (~7 bars/day) | `$1.49` | `$31.26` | DERIVED |
| Nof1 (~156 bars/day) | `$33.18` | `$696.69` | DERIVED |

What exists is a one-off: `$34.24` per manual full deploy — 7 models over the 161-bar contest window [MEASURED].

The *daily* board is a rolling **one-day** window, not the month-long contest window. Its recurring figure is deliberately not computed: at hourly cadence that day holds ~7 bars, at Nof1 ~156, and those differ by `22x` [DERIVED]. Supplying a bar count produces it.

## How far the API bill can be pushed

Four levers, each measured for cost *and* for what it does to behaviour. The decision model never changes.

### 2a — per-step routing

Routing the mechanical steps from `deepseek/deepseek-v4-pro` to `nvidia/nemotron-3-nano-30b-a3b`, on measured token counts:

| | baseline | routed | Tier |
|---|---:|---:|---|
| cost per decision (steps 1-2) | `$0.002061` | `$0.000491` | DERIVED |
| saving | | `76.2%` | DERIVED |

**The compound effect runs backwards.** The obvious assumption is that a cheap model is terser and shrinks every later step's input. Measured, it is the opposite: `nvidia/nemotron-3-nano-30b-a3b` emits `1458` output tokens at step 1 against `1197` for `deepseek/deepseek-v4-pro` [MEASURED], and `_build_step_prompt` embeds that verbatim in every later prompt. Routing step 1 to the cheaper model **inflates** downstream input.

**The parse rates do not support deployment.** Every measured cell was `15/15` [MEASURED], which by the rule of three bounds the per-step failure rate at `20.0%` at 95% confidence — not at zero [DERIVED]. At `156` decisions/day that ceiling is far too loose to act on; it needs hundreds of attempts per cell, not fifteen.

**No end-to-end saving is stated.** The decision step's parse rate is unmeasured — both models scored `0/15` there against a content-free fixture because of the empty-orders defect, which measures the pipeline and not the model [MEASURED]. Without it there is no completion rate, and a saving without a completion rate is not a result.

**A cap only saves where it binds, and breaks where it bites.** A cap above a step's natural output length costs nothing and saves nothing; below it the JSON truncates and the decision aborts with no retry. Every safe row above is a cap that never bound — the small non-zero reductions on those rows are run-to-run variation in how much the model chose to write, not an effect of the cap [MEASURED]. Hence `0.0%` max safe reduction for both models.

**So 2b is a dead end as measured.** There is no cap that both binds and survives. Step 2 emits ~`300` tokens naturally, so any cap that would save anything there is already below the break point; step 1 emits ~`1,300` and collapses the moment a cap reaches it [MEASURED]. The lever attacks the right cost term and has nowhere to stand.

One mechanism is worth recording: at tight caps the dominant failure is `empty`, not `truncated`. Both models are reasoning models, so a small budget is consumed by thinking tokens and no answer text is emitted at all [MEASURED].

### 2c — eliminated calls

The only lever with no behaviour cost: a cache hit returns the identical stored result, faster.

**Backtest caching cannot be sized.** A cache saves exactly the repeat rate and nothing else, and no telemetry records how often users re-run an identical backtest [NOT MEASURED]. An assumed rate here would put an invented number at the centre of the saving, so it is refused.

**Leaderboard governance saves `$0` recurring** [MEASURED], because nothing is scheduled to run. It prevents future recurring cost if a scheduler is added; claiming a saving against a schedule that does not exist would be counting money nobody is spending.

### 2d — dropdown composition (not an engineering change)

Models users cannot select cost nothing. The measured span is `193x` [MEASURED] — see the table in 2b for the per-model figures.

This is the advisor's call, not an engineering change. What it costs in capability is unknown: one evaluation window could not establish that the expensive models trade better (Spearman rho `+0.071`, intervals overlapping) [MEASURED].

### The stacked ceiling, and what it leaves

Caps contribute nothing, so the stack is routing alone: `76.2%` [DERIVED] — and that is an upper bound that overstates, for the reasons below.

Applied to a `$600,000`/month all-seven-models Nof1 figure it would leave `$142,778`/month [DERIVED]. **Read that as a floor on what is left, not a forecast.**

- routing_applicable_fraction is blank [NOT MEASURED], so the stacked figure assumes routing applies to ALL spend. That is its most generous reading and it overstates in two ways. (1) Routing applies only to multi-step pipelines and no telemetry records what fraction of user agents run more than one step. (2) The routing saving is measured on the MECHANICAL STEPS ONLY — the decision step keeps the expensive model by design — so the share of a pipeline's cost it can touch is strictly less than 100%, and that share cannot be computed without the decision step's measurement, which does not exist.
- output caps contribute NOTHING to the stack: every cap that reduces tokens breaks the parse, and the only safe cap is one that does not bind. The stacked figure is routing alone.
- the levers overlap. A cap applied to a step already routed to a cheap model saves cheap-model dollars, not expensive ones, so multiplying the fractions overstates the combined effect.

**Only model choice reaches the right order of magnitude.** Every engineering lever put together is well under `3x`; the per-call span across the roster is `193x` [MEASURED]. A 60-70% reduction on a $600k/month bill is still ~$200k/month. The decision that changes the order of magnitude is which models are offered at all — which is the same decision as open-weight substitution, and it rests on evidence that does not exist yet.

## What is deliberately not modelled

- **Prefix caching.** Measured at zero cached tokens over `160` requests against a `99.4%` shared-prefix fixture, `stats_source` null on both vLLM builds tested [MEASURED]. No saving modelled.
- **Sampling, staggering, skipping bars.** Experiment-only. On a user's agent it is indistinguishable from the product being broken.
- **Self-hosting.** A separate experiment in different units.
- **Any fallback-rate adjustment.** Unrecoverable from stored data in either direction.
