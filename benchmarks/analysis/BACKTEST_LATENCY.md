# Where a backtest's five minutes goes

Generated by `analysis/make_latency_report.py` from two traced runs. Instrumentation is monkeypatched at runtime by `analysis/backtest_latency_trace.py`; nothing under `dashboard/` was edited [MEASURED].

## 1. The hypothesis was right, and understated

The standing explanation — sequential LLM calls, one per bar — is confirmed. It is not `60%` of the wall clock. It is effectively all of it.

| run | window | bars | LLM reqs | reqs/bar | bar-loop wall | LLM time | LLM share | Tier |
|---|---|---:|---:|---:|---:|---:|---:|---|
| A | 2026-04-01..2026-04-04, 2 sym | `14` | `38` | `2.71` | `252.8s` | `252.7s` | **`100.0%`** | MEASURED |
| B | 2026-04-01..2026-04-02, 1 sym | `7` | `7` | `1.00` | `33.5s` | `33.5s` | **`99.9%`** | MEASURED |

**Everything that is not an LLM call totals `0.86`s and `1.01`s** — market data, portfolio state, order execution, equity update, response parsing and database writes, combined [MEASURED]. There is no hidden `40%`. There is barely a hidden `2%`.

Startup is fixed and small: engine construction, data load and indicator computation together take `1.01`s and `1.37`s [MEASURED].

**Market data is prefetched, not fetched per bar.** `fetch_bars` is called exactly once per run [MEASURED]; `engine.py` builds `self.all_data` and a forward-filled `price_cache` before the loop starts. That avenue is already closed.

### Two things the hypothesis did not predict

**Per-call latency is higher than the assumed `1-3`s.** Measured mean `4.78`s and `6.65`s, median `4.67`s and `6.40`s [MEASURED].

**Calls per bar is not reliably `1.00`.** Run B measured `1.00`; run A measured `2.71` [MEASURED]. The only two call sites for `_request_trading_decision` are both inside the no-text retry loop (`portfolio_manager.py:377` and `:390`), so the extra requests are retries — the reasoning model intermittently returns thinking blocks with no text. Run A's console log was filtered before capture, so the retry lines themselves were not preserved; the mechanism is inferred from the call sites, not read from the log [DERIVED].

That variance matters on its own: a backtest's duration is not predictable from its bar count. The same model on the same engine took a different number of requests per bar in two runs an hour apart.

### Reconciling with the reported five minutes

Extrapolated to the `161`-bar seed window, these traces imply `12.8` to `48.4` minutes [DERIVED] — *longer* than the reported `~5` minutes, not shorter.

Five minutes over `161` sequential calls implies `1.86`s per call [DERIVED], which sits inside the assumed `1-3`s band. So the arithmetic behind the hypothesis was sound; this trace simply ran a slower gateway path than production. **The structural conclusion does not depend on the constant** — at any per-call latency, the LLM share measured here is `99.9%`+.

## 2. Can bars be decoupled? No — answer (b)

**Bars chain through portfolio state. Parallelising them changes what the backtest computes.** The dependency is total for LLM agents, not partial, and it is visible in four steps:

| # | site | what it does | Tier |
|---|---|---|---|
| 1 | `portfolio_manager.py:615` | `execute_actions` mutates `self.cash`, `self.positions`, `self.trades` | MEASURED |
| 2 | `portfolio_manager.py:105-112` | `get_portfolio_state` reads that mutated `self.cash` / `self.positions` | MEASURED |
| 3 | `portfolio_manager.py:297` | the market snapshot embeds `portfolio`, `current_holdings` and `recent_trades` | MEASURED |
| 4 | `validator.py:719-725` | `create_safe_prompt` serialises that snapshot into the prompt with `json.dumps` | MEASURED |

So bar *N*'s prompt text contains the fills produced by bar *N-1*. The prompt does not merely receive state — its instructions branch on it: `validator.py:452-455` says to generate BUY actions when `current_holdings` is empty and HOLD actions when it is not [MEASURED].

All three prompt builders inject the snapshot, so there is no LLM-agent configuration that escapes the chain [MEASURED]. There is no batching and no lookahead in the loop.

**This is separate from the within-decision constraint** [MEASURED]. Earlier work established that pipeline STEPS cannot be parallelised because a later step embeds all prior step outputs. A different axis: steps chain within a bar, and bars chain across the run. Both are sequential, for different reasons.

**Consequence:** bar-level concurrency is not a free speedup. Any parallel scheme computes a different backtest — one where decisions are made against stale or assumed portfolio state — and the result would need validating against the sequential answer before it could be published. That is a product decision, not an optimisation.

## 3. ziplime does not address this bottleneck

`Limex-com/ziplime` is a maintained Zipline fork: GPL-3.0, Python `3.12`+, `528` stars, last pushed `2026-08-13`, not archived [MEASURED]. It is a real project and it is being worked on.

**Its "native AI support" is strategy code generation, not LLM-in-the-loop decisions.** You describe a strategy in English, an LLM writes algorithm code once, and that code is then backtested conventionally. No LLM call occurs during backtest execution [MEASURED].

That is the opposite of ATL's workload. ziplime optimises the part that is already free here: it advertises a `2-5x` faster event loop via Polars [MEASURED], and the event loop in ATL is inside the fraction of a second that all non-LLM work occupies. Making that `5x` faster saves a rounding error.

| question | answer | Tier |
|---|---|---|
| addresses the measured bottleneck? | no — targets event-loop speed, which is `<3%` of wall clock here | DERIVED |
| supports LLM-per-bar decisions? | not as a designed feature; AI is used at authoring time | MEASURED |
| Python `3.12`+ / maintained? | yes to both | MEASURED |
| licence compatible? | **no** — GPL-3.0 against ATL's OpenMDW-1.0 | MEASURED |

**The licence alone is disqualifying** for linking it into ATL, and the fit problem is independent of that. Migration would also mean rewriting data adapters, the execution model and the agent interface — substantial work to speed up something that is not slow.

It may be an excellent engine. It is aimed at a different problem.

## 4. Options, ranked by reduction per unit of effort

| option | expected reduction | effort | changes RESULTS? | Tier |
|---|---|---|---|---|
| result caching (built, unmerged) | `100%` on repeat runs, `0%` on first | none — already written | no | DERIVED |
| faster model / gateway for backtests | proportional to per-call latency; the dominant term | low — config | **yes** — a different model decides | DERIVED |
| fix the retry amplification | up to the excess reqs/bar, `2.71` -> `1.00` in the worst observed case | low-med | no — same decisions, fewer wasted requests | DERIVED |
| shorter window / coarser bars | linear in bar count | low — config | **yes** — a different backtest | DERIVED |
| bar-level concurrency | large in principle | high | **yes** — see section 2 | DERIVED |
| engine replacement (ziplime) | `<3%` | very high | no | DERIVED |
| non-LLM optimisation | `<3%` ceiling | any | no | MEASURED |

**The top two rows are where the leverage is, and only one of them is free.** Caching is already written and changes nothing about results; it just needs merging. Everything below it either changes what the backtest computes or chases a `<3%` remainder.

**The retry row is the one nobody has looked at.** If run A's `2.71` requests per bar occurs in production, then roughly `63%` of backtest LLM time and spend is retries [DERIVED] — invisible in the cost model, because `llm_calls` counts them as real calls. It is worth measuring before it is worth fixing.

Anything that changes results is a product decision. Only caching and the retry fix are pure optimisations.
